# Security model and limits

## Objective and scope

Avoid shipping PHP in readable text and raise the cost of extracting it. Files are protected at rest and their authenticity is checked before decrypting them. There is no intent to create a trusted environment inside a server fully controlled by the adversary.

This is a prototype, without independent audit. The functional tests do not demonstrate the absence of vulnerabilities. It must not be sold as equivalent in maturity or resistance to a commercial encoder.

## Adversaries

1. **Someone who receives only the encrypted files:** receives no key that allows decryption. The content key is wrapped with the recipient's public key (X25519); without the private key it cannot be recovered. Signatures and GCM reject modifications of the recognized container.
2. **Someone who receives the files and the loader:** the loader is **generic and contains no secrets**. It is free and recompilable (that is the design). By itself it decrypts nothing: the recipient's X25519 private key is needed, which lives in the server's identity file, not in the binary. Having the engine or another developer's keys does not open packages meant for others.
3. **Administrator/root of the server:** can read the identity file (and therefore that server's recipient private key), capture the code after decryption, instrument Zend/OpenSSL, use debuggers, hooks or memory dumps, or change the loader. There is no absolute protection against them with this design.

Compromising a server's identity file affects the projects whose keys it contains. It does not reveal other recipients' X25519 keys nor the maker's signing private key. However, if several clients receive exactly the same source, recovering that source from one is enough to know the logic common to all.

## Implemented decisions

- AES-256-GCM with 128-bit tags; no content is delivered before checking authentication.
- Random 256-bit content key per `pack` operation.
- 96-bit content nonce derived from a file counter within each `pack`. The key is renewed on each `pack`: there are no collisions between files under a single key generated by the tool.
- The content key is wrapped **per recipient** with X25519 + HKDF-SHA256 + AES-256-GCM, using an ephemeral pair per wrapping. The recipient table is generated once per package and copied byte for byte into its files. Without the recipient's X25519 private key it is not unwrapped.
- The derivation (HKDF `info`) and the wrapping AAD authenticate the usage domain, version, project, release, the ephemeral key and the recipient's key: an entry is not valid for another recipient or another release.
- Each file signs the stub, header, its relative path, table and ciphertext with Ed25519. The loader contains no keys; trusted signers are configured separately, in a **per-installation trust store** (identity file), never taken from the package. Each developer is identified by `developer_id = SHA256(public key)` and may have an optional **recovery key**: a package signed by the primary or by the recovery verifies, which allows rotating a compromised signer without recompiling the loader. Trust is global per installation: the host accepts packages from any developer it has added to its trust store.
- **Anti-downgrade:** the v2 loader only accepts the `ENVLK02` magic/version 2 and rejects the v1 format. Magic and version are signed.
- Exact lengths, a 16 MiB source limit per file and 1024 recipients per package. The Zend flow may read the encrypted file before validating that limit; completely avoiding memory consumption against giant local files is not promised.
- The explicit decryption buffers and the intermediate keys (X25519 secret, wrap key, content key) are cleared with `OPENSSL_cleanse`/`OPENSSL_clear_free`. No temporary file of decrypted PHP is written.
- The identity file is loaded once at module start and is left read-only; each recipient key pair is checked there once. It is rejected if other local users can read it: on POSIX, any group/other permission bit or a different owner; on Windows (allow-list), an owner or any access entry other than the account PHP runs as, SYSTEM, Administrators or OWNER RIGHTS, or no DACL at all. A rejected file is reported with its reason in a startup warning and in the compile error. Boolean directives (`opcache.enable`, `envelock.allow_opcache`, …) are parsed exactly as PHP/OPcache parse them, so a quoted `"On"` cannot hide an enabled OPcache. OPcache's SHM cache is refused for protected files by default (opt-in via `envelock.allow_opcache` with `opcache.blacklist_filename`); `opcache.file_cache` and preloading are always refused. Decrypted source or opcodes are never kept between requests; each worker only caches package content keys and the hashes of already verified signatures.
- **Path binding and release consistency:** each file only runs from a location ending in its signed relative path (no renaming or swapping inside a package), and in one request all protected files under a package folder must share project and release (no file swapped in from another release or project).
- **Anti-rollback (opt-in per server):** each package carries a signed serial; a minimum per project in the identity file (`minimum set`) refuses older releases. On a host that trusts several developers, each minimum is **bound to the developer that set it**, so one trusted developer cannot set a rollback bar on another developer's project (ENV-AUD-14).
- **Include protection (opt-in per package, `--include-protection`):** a protected file only runs as the entry point or with a protected file of the same project **and signed by the same developer** on the call stack, so another script on the server — even one signed by a different developer trusted on the same host — cannot load it to call or inspect its code. The entry point is recognised under every SAPI (CLI, FPM/CGI and the Apache module), and a user-space stream wrapper cannot forge it. **`--no-prepend`** refuses `auto_prepend_file`/`auto_append_file`, which a site user can set through `.user.ini` or `.htaccess` to run code in the same request.
- **Debugging extensions:** Xdebug, VLD, uopz, runkit7, xhprof, tideways, ddtrace, SPX, pcov, blackfire, memprof, an installed `zend_ast_process` hook and the phpdbg SAPI make protected files fail closed unless `envelock.allow_debuggers=1` (a defence against careless configuration; an administrator can still instrument PHP). This list is a **best-effort deterrent, not a guarantee**: it deliberately does NOT refuse on the presence of a `zend_observer` consumer (the API behind New Relic, Datadog, Elastic APM, OpenTelemetry and Sentry native), a `zend_execute_ex`/`zend_execute_internal` hook or a custom opcode handler, because doing so would stop protected code from running under standard production monitoring. Anyone able to load such an extension can observe the decrypted code — which is adversary 3 (the administrator), explicitly outside the threat model (ENV-AUD-15).
- **Obfuscation (opt-in, `--obfuscate`):** local variable names inside functions are replaced by short ones; `--obfuscate-methods`/`--obfuscate-properties` also rename private members (properties are HIGH RISK with serialized data), `--obfuscate-flow` inserts always-false dead branches (modest; not control-flow flattening), `--obfuscate-flatten` rewrites plain function and method bodies into a dispatch loop (O6; a body that observes its frame — generators, `goto`, dynamic variables, `compact`/`extract`/`get_defined_vars`, `include`/`eval`, nested declarations — is left as written and reported; it is not a proof that the control flow is unrecoverable: a reader can follow a switch-based dispatcher), and `--obfuscate-names` renames the classes, interfaces, traits, enums and functions the package declares together with every reference to them — which makes the package self-contained, so anything outside it that names those symbols stops working (test the deployed package). It only renames what can be proved closed: a name is left alone if it appears in any string literal of the package (a string is how PHP spells `class_exists()`, a Reflection lookup or a serialised class name), if it is a builtin (the whitelist is the running PHP's own symbol table), if it starts with `__`, or if a method or class constant already spells it; and the whole package is skipped if any file uses `namespace`, `eval()`, `global`, a variable function call or variable-variable interpolation. What still reveals structure: class constants, public member names without `--obfuscate-methods`, and the control-flow shape of every function.
- **Deployment licenses (opt-in, objective O8):** `envelock.licence` names a fixed-size file signed with the owner's Ed25519 key — a key the server already trusts, because it is the one that signs packages. A license can only narrow what the loader runs, never widen it, so a self-issued license is worthless to an attacker and the loader refuses one whose signature does not come from a trusted key. Once the directive names a file the license is mandatory: a missing or unusable file fails closed. The directive itself, like every license control, lives in `php.ini`, which belongs to the server's administrator, and the loader is open source — so a license keeps a deployment operated as agreed within its terms; it is not DRM against the server's own administrator. Expiry is re-checked every time a protected file is compiled (per request under PHP-FPM, Apache or CGI); code already compiled in a long-lived process (daemon, queue worker, Swoole/RoadRunner/FrankenPHP worker mode) keeps running until that process restarts. Machine binding is SHA-256 over `/etc/machine-id` plus the sorted MAC addresses of the physical interfaces, derived only from what the host already reports — a value Envelock stored itself would prove only that it was copied along with the license; both inputs can still be set by the administrator, and in a container the fingerprint is the image's `/etc/machine-id` alone. Two further constraints are offered for commercial parity and are **not** equally strong. *IP* binds the server's own IPv4 addresses: not something a remote caller chooses, but it breaks whenever the addresses change. *Domain* binds the served host name, taken for a web request from `SERVER_NAME` — the name the web server is configured to serve, not the client's `Host` header (but Apache with the default `UseCanonicalName Off` derives `SERVER_NAME` from that header) — and on the command line from the machine's own host name, never from the environment; it stops a copied deployment from working by habit, and it is not access control. **Honest limits:** expiry is compared against the local clock; `envelock.clock_state` records the highest time the installation has been seen running at and refuses a clock behind it, which defeats `date -s`, but the record is a file on the server and its administrator can delete it — and signing it would not help, since every key the loader holds is on that same server. `envelock.trusted_time` raises the bar further by taking a floor on the real time from the `Date` header of any HTTPS host, authenticated by the TLS session (chain and host name verified; certificate dates deliberately not checked against the suspect local clock), once per process start; it also pushes the watermark forward, so deleting the state file is no longer enough, and a network time more than a day ahead of the local clock refuses protected files rather than being ignored. A host that cannot be reached records no observation and never refuses a site. It remains a floor rather than a ceiling, and an administrator who controls the machine's DNS and trusted CAs can still answer with a chosen time; the fingerprint is computed twice, in Python when issuing and in C when checking, and a drift between the two would refuse every machine-bound license, which is why the test suite compares them on the host running the tests; and on Windows the loader has no machine, host-name or IP lookup (nor a trusted-time fetch), so a license bound to any of them is refused there.

- **String-literal confidentiality (opt-in):** `--encode-strings` re-spells literals as `\xNN` (hides them in the source text, but the decoded value is still a constant in the compiled op_array). `--vault-strings` goes further: literals in a runtime position are moved out of the code into a per-file vault the loader resolves (`\__envelock_lit(idx)`), so they are **not** a constant in the compiled op_array nor present in the decrypted source the engine compiles, and the loader wipes them from memory at the end of each request. Honest limit: both only raise the cost of recovering strings from the compiled code and the source; neither defeats someone who can read the process memory (the administrator — outside the threat model, and already reduced by `harden_memory`). Literals in constant expressions stay inline. **Objective O7** adds a layer inside that vault: the table itself is encrypted (AES-256-GCM under a per-file data key, wrapped with the package content key) and each literal is decrypted only when the program reads it, so the decrypted container holds ciphertext rather than every secret string in the file lying in one contiguous block. Measured: flipping one byte of an entry's ciphertext costs the attacker that literal — the tag fails and the loader returns the empty string, as for any vault miss, rather than handing over corrupted bytes or failing the request. Honest limit, unchanged: the data key is wrapped with the content key, so a reader who can decrypt the container can unwrap it, and a reader who can run the code or dump the process at the right moment still gets whatever has been decrypted. What O7 removes is the cheap attack — read one already-decrypted block, get every string in the file.
- **Runtime manifest enforcement (on by default; `--no-manifest` to opt out):** `pack` writes a signed binary manifest by default, and the loader verifies it on the first protected file of each request and refuses to run if any listed file is missing, so a deleted or renamed-away file (e.g. an authorization check) is caught; it is not a full deployment sandbox (see below).
- **Mini-VM (O4): quarantined, not production-ready.** Differential testing shows observable
  differences from PHP despite delegating some operations to Zend. The CLI/API refuses virtualization
  unless a clearly unsafe laboratory-only override is supplied, together with a probed V2 loader;
  it also refuses the combination with public name obfuscation. A rebuilt loader rejects V1 VM
  programs. Earlier V2 programs are refused by the V3 loader: they used eager local reads and had compiler bugs
  (skipped `else` branches, misordered operands, late undefined-variable warnings). Repack from
  source only for research.
  V3 programs that use a plain local key in a dimension chain (opcode 0x15) need a loader built from the same source; an older V3 loader rejects them as an unknown opcode.
  Function calls (`INIT_CALL` 0x16, `CALL` 0x08) compile only for builtins measured to match PHP when called directly; Zend's special-cased builtins, `min`, `max`, `implode`, frame-sensitive functions, by-reference parameters and files with `strict_types` or a namespace are refused. A loader without 0x16 refuses such programs. Warning order in concatenation and ternaries follows PHP as measured (see MANUAL §14.4). These are measured cases, not a proof of equivalence.
  The old prebuilt loader is not repaired and must
  not be used for VM. The compiler checks reachable instruction paths against the stack limit;
  the loader separately checks stack bounds at runtime. Accepted programs and combinations with
  other transformations are not proven safe. The instruction stream is encoded, not encrypted, and can
  be observed during execution. See [MANUAL.md §14.4](MANUAL.md#144-mini-vm-o4-quarantined-laboratory-only).

## What these measures do NOT guarantee

- Erasure of all copies: PHP keeps literals, names, opcodes and other data; the system may produce swap/core dumps. (`zend.multibyte` is now refused for protected files, since its scanner would keep an uncleared copy of the source; a `ParseError` message can still contain fragments of the source.) The Python encoder also does not guarantee erasure of its objects in memory. All of these are only reachable by someone who can read the PHP process memory or its logs (the server administrator, outside the threat model). `envelock.harden_memory` (on by default) reduces this exposure: it locks the loaded private keys into RAM, excludes them from dumps, and marks the process non-dumpable (no core dumps, no `ptrace`/`/proc/self/mem` reads by the same user); it is re-applied after startup so it survives a worker dropping privileges. Set it to `0` to allow a legitimate profiler or core dump. `envelock.paranoid` (opt-in, off by default; objective O3) goes further and refuses a protected file when the process is being instrumented at run time rather than by a recognisable loaded extension: a `ptrace` tracer, a replaced `zend_execute_ex` or `zend_interrupt_function`, or a registered execution observer. Two related checks always run regardless of the flag: that Envelock's own compile hook is still the one it installed at startup, and that no `zend_ast_process` hook is installed — an extension loaded after Envelock can otherwise sit above it and read the handle it has just decrypted. Honest limits: a tracer that *stops* its target is invisible to any in-process check (a stopped process cannot run the check; measured — `TracerPid` reads 0 before and after, never during), so only a tracer that leaves the target running is caught; and every check here is advisory, since an attacker who owns the process owns the checks.
- Invisibility of the algorithm: the source is reconstructed in memory. An AST/compiler hook or a modified PHP can observe it.
- Impossibility of copying: the loader+package pair can be moved to another compatible machine. There is no physical binding or attestation.
- Licenses with expiration, counters, revocation or domain control. The identifiers are not complete commercial licenses.
- Anti-rollback without a configured minimum: until `minimum set` is used for a project, an old, correctly signed release of it remains valid.
- Integrity of the whole deployment: a tampered signed file is rejected if it is recognized as a container, but someone with write access can replace it with normal PHP, delete files or modify assets. The loader allows unprotected PHP for compatibility. There is no signed global manifest that forces the use of a closed set of files.
- Include protection against plain code inside your call stack: plain files that protected code includes or calls (configuration, `vendor/`, callbacks) run with protected frames below them, so whoever can modify them can load and inspect protected code; keep them write-protected. It also does not fit deployments whose entry point is unencrypted.
- A sandbox between projects: path binding works within a package folder; a whole package folder can be replaced by another package addressed to the same server, and projects can include files of other authorized projects (without include protection).
- Protection of dynamically downloaded/generated code or of business secrets/configuration that have not been encrypted.

`envelock-package.json` is diagnostic information, not a license nor an authenticated manifest. The necessary cryptographic authorization is inside each signed container. No external `licencia.bin` is needed.

## Custody and distribution

**Never deliver/publish:** `owner.json`, recipient descriptors (`recipient*.json`), server identity files (`identity*.bin`), original sources, compilation objects, encoder caches, sensitive logs, debug symbols or backups of these files. The loader module is public (generic, without keys).

**Binaries in this checkout.** Compiled files are restricted by `scripts/check_release.py` to allowed, manifest-listed areas, with third-party files also checked against their manifest. In the complete distribution `prebuilt/` holds the loaders for every supported engine/platform (five Linux `.so`, eight Windows `.dll`), the Linux and Windows assistants, the portable Python distributions and the wheel bundle, each listed in `prebuilt/SHA256SUMS`; the source-only distribution ships none of them. See [prebuilt/README.md](../prebuilt/README.md). The Python/OpenSSL upstream source trees are not included in either. Install trusted dependencies against `requirements.lock`; this checks downloaded artifacts against the recorded hashes, but does not authenticate the repository or its lock file. The optional launchers use `-E -s` if a separately supplied portable interpreter is present; protect that interpreter and its libraries against modification. A hash list stored alongside a binary proves consistency, not origin: verify the source and distribution before trusting it.

The server's identity file contains the recipient's X25519 private key: protect it with `0600` permissions, the right owner and outside the document root. Anyone who reads it can decrypt the packages addressed to that server.

Use a trusted packaging machine, encrypted disk, a dedicated user, restrictive ACL/permissions, encrypted backups and private CI with no traces of secrets. Private JSONs are encrypted by default (scrypt with fixed parameters and AES-GCM); the unencrypted mode requires an explicit `--no-encrypt`, prints a warning, and is meant only for throw-away test material. Strong passwords, backups and ACLs are still necessary. Do not put keys or passwords in shell parameters: the commands receive paths, not key values; `ENVELOCK_PASSWORD_FILE` points to a restricted file.

To produce binaries, compile without `-g` and apply each platform's hardening and code-signing practices after validating them. Stripping symbols modestly increases difficulty, it does not constitute a cryptographic barrier. Keep OpenSSL/PHP and dependencies up to date and review licenses when redistributing libraries.

**Assistant network access.** The encoder never uses the network; the loader does only when `envelock.trusted_time` is set (one HTTPS `HEAD /` per process start, to the host you name; MANUAL §14.3). The graphical assistant connects only when you accept one of its two offers, both on Windows: downloading PHP 8 from the official php.net release index over HTTPS (the ZIP is accepted only if its SHA-256 matches that index, and members with absolute paths or `..` are rejected on extraction), and installing Microsoft's Visual C++ runtime from Microsoft's address (the installer runs only if its Authenticode signature is valid and issued to Microsoft; otherwise it is deleted unrun). The SHA-256 check relies on the HTTPS index; if you need an independent check, install PHP yourself and choose it with *Browse*. Your keys and sources are never sent anywhere.

On the server: limit privileges, separate PHP-FPM pools, restrict ptrace/core dumps according to the system's policies and prevent the document root from including private materials. These measures mitigate operational incidents, they do not turn root into an adversary unable to inspect the process.

## OPcache: the measured reality and the opt-in

OPcache caches the **already-compiled opcodes** —the program after decryption— in shared memory (SHM) reused between requests. `opcache.file_cache` persists them **to disk**; preloading leaves them resident when the server starts; the JIT compiles them to machine code in that same memory. Any of those paths leaves the decrypted program (as recoverable opcodes) outside Envelock's control.

**What was measured.** OPcache re-asserts itself as the *outermost* `zend_compile_file` hook on every request (its per-request activation), so Envelock cannot reliably sit above it, and compiling protected files through the real Zend compiler to bypass it does **not** stop OPcache caching them (confirmed empirically; converting Envelock into a `zend_extension` does not change this). The only reliable way to keep decrypted opcodes out of SHM is `opcache.blacklist_filename` covering the protected tree (measured: the protected file is then **not** cached while the rest of the app still is).

**Behaviour.**
- `opcache.file_cache`, `opcache.file_cache_only` and `opcache.preload` are **always refused** for protected files (they persist decrypted opcodes to disk or resident SHM). Compiling a protected file with any of them set raises `E_COMPILE_ERROR`.
- OPcache's SHM cache is **refused by default** (fail closed) whenever OPcache would cache: `opcache.enable` on and, for the CLI/phpdbg SAPIs, `opcache.enable_cli` on too (the same rule OPcache applies, with the same boolean parsing). A protected file then raises `E_COMPILE_ERROR` telling the operator to disable OPcache or opt in. The CLI with the stock defaults (`enable_cli=0`) does not cache and runs protected files.
- Setting `envelock.allow_opcache=1` (PHP_INI_SYSTEM) lets protected files run with OPcache's SHM cache enabled. This is an explicit assertion by the operator that the protected tree is excluded via `opcache.blacklist_filename`. As a backstop the loader also detects, on the first compile of each file, that OPcache is about to persist it to SHM (`ZEND_COMPILE_IGNORE_OTHER_FILES` is set only then, not for a blacklisted file) and fails closed with a clear error, so a missing or wrong blacklist no longer lets decrypted opcodes sit silently in SHM. The blacklist is still the mechanism that lets the protected tree run with OPcache on; the backstop only turns an operator mistake into a hard failure instead of a silent exposure. `opcache.file_cache` and preloading stay always refused.

**Recommended operation.** Run the protected application in a dedicated PHP-FPM pool. Either disable OPcache there, or set `envelock.allow_opcache=1` **and** `opcache.blacklist_filename` to the protected tree, and verify with `opcache_get_status()` that protected files are not listed as cached. Note that blacklisted protected files are re-decrypted on every request (OPcache does not cache them), while the rest of the application benefits from OPcache; a per-worker cache of decrypted protected files is future work. As operator hardening, keep `enable_dl=Off` and the `php.ini` not writable by the application user, so another extension cannot be loaded into the pool to observe the decrypted code, and restrict `open_basedir` to the application tree.

- The quarantined mini-VM is not for production; unmarked packs are unaffected. Its runtime cost
  depends on the workload; a single microbenchmark is not a general performance guarantee.

## Performance

The loader decrypts each protected file at the moment of compiling it, and since protected files are not cached by OPcache (disabled or blacklisted), that cost is paid on **every request**. The v2 asymmetric model adds one X25519 + HKDF operation per file compared with the earlier symmetric model. The measured figures (per-file cost, comparison with unencrypted PHP and the share attributable to the asymmetric part) are in [VERIFICACION.md](VERIFICACION.md#measured-performance). Memory: the loader's own use is small and transient (each file is decrypted in place, so it is never held twice; cleared and freed after compiling it; no code is kept between requests; no leaks measured), but the compiled code of protected files lives in each request's memory instead of OPcache's shared memory ([measured](VERIFICACION.md#measured-memory)). Operational recommendation: encrypt only your own code (leave framework/`vendor` to OPcache), size `memory_limit` and PHP-FPM with the measured memory per request, consider `pack --strip-comments` (docblocks are kept in the compiled code otherwise), and prefer fewer, larger files; measure with your real application. Safe integration with OPcache is still pending research.

## Pending before production

**Bytecode payload (`pack --bytecode`, objective O1).** A protected file can carry a serialized
`zend_op_array` instead of encrypted source (format flag bit 6, see FORMATO.md). On the server the
loader deserializes the image and runs it: the compiler is never invoked for that file, so there is
no decrypted PHP source in the process for a `zend_compile_file` hook, a modified engine or a memory
reader to recover. Verified on PHP 8.4: a package built this way runs a test application with output
identical to the plain sources, and no PHP text — neither syntax nor the program's own identifiers —
appears anywhere in the package. Identifiers still exist inside the image (they are the program);
hiding them is the obfuscator's job (objective O6), which runs *before* the bytecode is produced.

What it costs and what it binds, stated plainly because both are load-bearing:

- An image only loads on the **PHP version and build** that produced it (a bytecode identity over
  the version, the Zend extension build id, the data layout and the VM kind, checked before anything
  is dereferenced; not `zend_system_id`, which varies between the SAPIs of one build). A different
  build refuses the file rather than misrunning it, so a bytecode package must be repacked per target
  build; a CLI-packed image runs under `php-cgi`/PHP-FPM of the same build.
- `__DIR__`, `__FILE__` and statically resolved include paths are **compile-time** values baked into
  the image. `--bytecode` therefore requires `--deploy-root` and compiles each source at its deploy
  path (removing it again), and the package then only runs from that path. This is inherent to
  precompiled bytecode — OPcache's own file cache is path-bound the same way.
- An image is roughly ten times the size of its source (about 7.7× after `zlib -9` on a 5.7 KiB
  file), and two compilations of the same source do not yield a byte-identical image (~1% of the
  bytes differ). The latter is a property of the OPcache serialization being reused — upstream's own
  `file_cache` differs in 187 bytes of the body for the same source — and does not affect behaviour.
- Each request decrypts the image into request memory and deserializes it there, so the decrypted
  program lives exactly as long as the request and is gone when it ends. It used to be a
  process-lifetime block, which leaked one image per file per request in a long-lived worker
  (measured: about 25 kB per request, so a worker serving a few thousand requests would have grown
  by tens of MB); a test now fails if that comes back.
- What is still open is the other half of objective O9: a per-worker cache that would let a file be
  deserialized once per worker instead of once per request. It cannot be built by keeping the
  image, because deserializing consumes its input — the map-pointer slots stop being offsets and
  become pointers into that request — and it cannot be built by keeping the deserialized script
  either, because `envelock_load_script()` binds class entries and early bindings into the request
  that loaded it and a second request dereferences them after they are freed (a segmentation fault
  in `zend_verify_return_error`, reproduced). Upstream OPcache can do it because its scripts live
  in shared memory with machinery this vendored copy does not carry. So bytecode currently pays
  deserialization per request, and the numbers below are honest about that.

Measured cost, with `scripts/bench.py` on PHP 8.4.27 (300 files of ~1.9 KB included inside one
process, OPcache off, best of 7 runs): 25 µs/file plain, 179 µs/file protected in source mode,
174 µs/file in bytecode mode — **at parity**, the difference being within run-to-run noise. The
per-file cost is dominated by the container (unwrap, decrypt, verify), not by compiling, so the
engine-level gain from not compiling (94.5 µs to load an image against 534.4 µs to compile one
5.7 KiB source, measured in process) does not show up at this file size. The bench starts a fresh
process per run, so it measures the cold path; the warm path cannot be measured inside one process
at all, because PHP refuses to declare the same function twice and a package therefore cannot be
loaded twice by one worker. Bytecode is not slower than what it replaces, which is the bar this
project sets, and the gain it is meant to bring waits on the cache described above.

**Secret memory for the private keys (`envelock.secret_memory`, objective O2).** The identity private
key is the one thing in the process that decrypts everything addressed to this installation, so it
does not sit in `.bss` with the rest of the module. With the directive on it lives in a region
backed by `memfd_secret(2)`: the kernel takes those pages out of its direct map, so they are absent
from `/proc/PID/maps`, `/proc/PID/pagemap` and `/proc/kcore` — there is no linear address to read
them through. That is strictly stronger than what the process already does, and the difference is
concrete: `PR_SET_DUMPABLE(0)` plus `mlock` plus `MADV_DONTDUMP` stop a core dump and an ordinary
same-user `ptrace`, but a reader with `CAP_SYS_PTRACE` can still read a normal mapping through
`/proc/PID/mem`. Measured on Linux with the directive on and memory hardening off, `/proc/PID/status`
reports `VmLck: 64 kB` for the arena and `0 kB` with it off; with hardening on, `/proc/PID/maps`
becomes unreadable even to the process's own user, which is the dumpable flag working as intended.

Stated plainly, because a guarantee that cannot be checked is worth nothing:

- **`memfd_secret` is frequently unavailable.** It needs `CONFIG_SECRETMEM` and a kernel that can
  split its direct map into small pages; where it cannot, the syscall is not registered and returns
  `ENOSYS` — a kernel can be built with `CONFIG_SECRETMEM=y` and still not offer it. The arena then
  degrades to an anonymous `mlock`'d, `MADV_DONTDUMP` mapping, which is the protection this
  extension already had, and `envelock_secret_memory()` reports exactly which of the two is in use.
  A deployment turns the directive on and reads that back on the real server.
- **The secrecy itself was not verified here.** The development kernel returns `ENOSYS`, so the
  primary path is exercised in the test suite by answering the syscall with `memfd_create(2)` at
  link time (`-Wl,--wrap=syscall`), which runs every line around it — the `ftruncate`, the
  `MAP_SHARED` mapping, the `FD_CLOEXEC` on the fd, allocation, exhaustion, wipe, teardown — but
  cannot demonstrate that the pages leave the direct map. That needs a kernel that offers the
  syscall, and is on the verification list.
- The arena is bumped, never freed: a block is never handed out twice, so nothing retired is left
  readable for a later allocator. It is wiped and unmapped at module shutdown.

Cryptographic and C/Zend audit; fuzzing with ASan/UBSan and a malformed signed corpus; review of lifecycles in fatal errors; multithread/ZTS testing; FPM/Apache SAPI; stress and performance; native Windows/macOS matrix; compatibility with extensions that intercept compilation; update strategy and binary signing; secret management/rotation and recovery after compromises.

If a part must remain secret even against the server owner, it must not be executed as decrypted PHP under their control. This requirement cannot be achieved by adding more AES layers to the same offline loader.
